# Врайтап: chall — флаг внутри виртуальной машины

Oct 25, 2026 · @Demian

## Кратко

Флаг не хранится в бинарнике строкой: его проверяет байткод маленькой виртуальной машины, и каждый символ после нескольких add/xor/sub должен стать нулём. Значит, символы можно подобрать по одному.

- **Категория:** reverse
- **Файл:** `chall`, ELF x86-64, PIE, stripped
- **Описание:** «I found that having the flag in plaintext was too obvious, so I felt like I had to hide it a little bit.»
- **Поведение:** печатает ` Input:  `, читает строку и отвечает `Correct!` или `Wrong...`

Флаг:

```
flag{M4yb3_w3_c4n_74k3_0n_3v3n_70ugh3r_ch4113ng3$_n0w?}
```

## Разведка

В строках флага нет, есть только четыре сообщения, и среди них подозрительное `Error...`.

```
$ file chall
chall: ELF 64-bit LSB pie executable, x86-64, dynamically linked, stripped

$ strings chall | grep -i flag
$                         # пусто

$ strings -n 6 chall
...
Correct!
Wrong...
Input: 
Error...

$ echo test | ./chall
Input: Wrong...
```

Из libc импортированы только `fgets`, `strcspn`, `strlen`, `putc`, `puts` и `__printf_chk`: ни `strcmp`, ни `memcmp`. Значит, сравнение сделано вручную. В `.rodata` (`0x2000`) после строк лежит длинный массив из четвёрок байтов вида `07 00 xx 00`, `06 00 xx 00`. Это похоже на байткод, так что идём в дизассемблер (`objdump -d -M intel`). Функция `main` начинается с `0x1120`: на неё указывает `lea rdi` перед `__libc_start_main` в `_start`.

## Главная функция

`main` читает строку и крутит цикл диспетчера над байткодом с адреса `0x2080`. В конце проверяются два условия: длина ввода равна 55 (`0x37`) и регистр `r7` равен нулю. Вот как это выглядит в псевдокоде после разбора:

```c
char buf[64] = {0};
printf("Input: ");
if (!fgets(buf, 64, stdin)) return 1;
buf[strcspn(buf, "\n")] = 0;

input     = buf;          // 0x4040
input_len = strlen(buf);  // 0x4030
input_pos = 0;            // 0x4038
uint8_t r[8];             // 0x4048..0x404f, r[7] = 0x404f

pc = 0;
for (;;) {
    op = code[pc]; a = code[pc+1]; b = code[pc+2]; c = code[pc+3];
    if (op == 0xff) break;                          // конец программы
    if (op == 0 || op > 13) { puts("Error..."); break; }
    target = (c << 8) | b;                          // адрес для переходов
    switch (op) { /* таблица переходов на 0x2040 */ }
    pc += 4;                                        // если переход не взят
}
puts(input_len == 55 && r[7] == 0 ? "Correct!" : "Wrong...");
```

Как это видно в ассемблере:

- **Выборка** — `0x1220`: четыре `movzx` из `[rbx+rdx]`, где `rbx = 0x2080` (байткод), `rdx` — счётчик команд. Байты идут в `al` (op), `sil` (a), `dil` (b) и `cl` (c).
- **Адрес перехода** — `0x11e8`: `shl ecx, 8; or ecx, dil`, то есть 16-битное число `c:b`.
- **Диспетчеризация** — `0x11fa`: `movsxd rax, [r9+rax*4]; add rax, r9; jmp rax`, где `r9 = 0x2040`. Это обычная таблица относительных смещений от `switch`.
- **Следующая команда** — почти каждый обработчик заканчивается `jmp 0x12a0`, то есть `add rdx, 4`.
- **Финал** — `0x123f`: `cmp [0x4030], 0x37`, потом `cmp byte [0x404f], 0`. Оба совпали — печатается строка с `0x2004` (`Correct!`), иначе с `0x200d` (`Wrong...`).

Мелкая деталь: перед циклом регистры x86 уже содержат `op=1, a=7, b=0` (`mov eax,1; mov esi,7; xor edi,edi`). Это заранее декодированная первая инструкция байткода `01 07 00 00`, то есть `r7 = 0`.

## Устройство VM

У машины 8 однобайтовых регистров `r0`–`r7` по адресу `0x4048` и 14 опкодов плюс `0xFF` для остановки. Каждая инструкция занимает 4 байта:

```
+------+------+------+------+
|  op  |  a   |  b   |  c   |
+------+------+------+------+
  a     — номер регистра-приёмника
  b     — константа или номер второго регистра
  c:b   — 16-битный адрес перехода (смещение от 0x2080)
```

Таблица переходов на `0x2040` — это 14 знаковых 32-битных смещений. Если прибавить каждое к `0x2040`, получатся адреса обработчиков:

| op | Обработчик | Ключевая инструкция | Семантика |
| --- | --- | --- | --- |
| 0 | — | `test al,al; je 0x139f` | `Error...` |
| 1 | `0x138f` | `mov [r+rsi], dil` | `r[a] = b` |
| 2 | `0x1363` | `mov cl,[r+rdi]; mov [r+rsi],cl` | `r[a] = r[b]` |
| 3 | `0x1350` | `add [r+rsi], cl` | `r[a] += r[b]` |
| 4 | `0x132a` | `sub cl,[r+rdi]` | `r[a] -= r[b]` |
| 5 | `0x1314` | `xor cl,[r+rdi]` | `r[a] ^= r[b]` |
| 6 | `0x1340` | `add [r+rsi], dil` | `r[a] += b` |
| 7 | `0x1307` | `xor [r+rsi], dil` | `r[a] ^= b` |
| 8 | `0x12d3` | `movzx ecx,[input+pos]` | `r[a] = input[pos++]`, или 0, если ввод кончился |
| 9 | `0x12a9` | `call putc` | вывести `r[a]` |
| 10 | `0x1284` | `or cl,[r+rdi]` | `r[a] \|= r[b]` |
| 11 | `0x1215` | `movzx edx, cx` | `pc = c:b` |
| 12 | `0x1275` | `cmp [r+rsi],0; jne skip` | если `r[a] == 0`: `pc = c:b` |
| 13 | `0x1204` | `cmp [r+rsi],0; je skip` | если `r[a] != 0`: `pc = c:b` |
| 0xFF | — | `add al,1; jne error` | стоп, переход к финальной проверке |

`r` в таблице — база регистров `0x4048`. Регистр `rsi` хранит `a`, `dil` — `b`. Опкоды 0 и 1 в таблице ведут на один обработчик, но ноль отсекается раньше. Опкод 8 возвращает 0 после конца ввода. Поэтому сама программа не отличила бы короткий ввод от полного, и длина 55 проверяется отдельно в `main`.

## Байткод

Программа — это 294 инструкции без единого перехода и без `putc`: 55 одинаковых блоков по одному на символ. Дизассемблер пишется прямо по таблице опкодов:

```python
import sys
data = open(sys.argv[1], 'rb').read()
CODE = 0x2080
NAMES = {
    1: 'mov  r{a}, {b}',     2: 'mov  r{a}, r{b}',
    3: 'add  r{a}, r{b}',    4: 'sub  r{a}, r{b}',
    5: 'xor  r{a}, r{b}',    6: 'add  r{a}, {b}',
    7: 'xor  r{a}, {b}',     8: 'read r{a}',
    9: 'putc r{a}',          10: 'or   r{a}, r{b}',
    11: 'jmp  {t:#06x}',     12: 'jz   r{a}, {t:#06x}',
    13: 'jnz  r{a}, {t:#06x}', 0xff: 'halt',
}
pc = 0
while True:
    op, a, b, c = data[CODE + pc:CODE + pc + 4]
    print(f'{pc:04x}:  {op:02x} {a:02x} {b:02x} {c:02x}   ' +
          NAMES.get(op, '???').format(a=a, b=b, t=(c << 8) | b))
    if op == 0xff:
        break
    pc += 4
```


Каждый блок устроен одинаково:

1. `read r0` — взять очередной символ.
2. Три преобразования в разном порядке: `add r0, k`, `xor r0, k` или `mov r1, k; sub r0, r1`. Вычитание идёт через `r1`, потому что у VM нет опкода «вычесть константу».
3. `or r7, r0` — если символ не обнулился, в `r7` появятся единичные биты, и сбросить их уже ничем.

Итого 55 `read`, 55 `or`, 110 `xor`, 38 `add` с константой и 17 пар `mov`/`sub`. `r7 == 0` в конце означает, что каждый из 55 символов после своих трёх преобразований стал ровно `0x00`.

В самом байткоде цикла нет: 55 блоков просто идут подряд, а длину и `r7` после `halt` проверяет уже `main`.

## Решение

`add`, `sub` и `xor` по модулю 256 обратимы. Значит, у каждого блока ровно один символ, который превращается в 0. Чтобы его найти, достаточно начать с 0 и пройти операции в обратном порядке: `xor k` → `xor k`, `add k` → `sub k`, `sub k` → `add k`.

Ручная инверсия для первых двух символов:

```
символ 0:  add 19, xor 119, xor 14
    0 ^ 14 = 14
   14 ^ 119 = 121
  121 - 19 = 102 = 'f'

символ 1:  sub 94, xor 33, xor 47
    0 ^ 47 = 47
   47 ^ 33 = 14
   14 + 94 = 108 = 'l'
```

Остальные 53 символа считает скрипт. Он разбирает байткод прямо из файла, так что константы вручную переписывать не нужно:

```python
import sys

data = open(sys.argv[1], 'rb').read()
CODE = 0x2080

# 1. Разбиваем байткод на блоки: всё между `read r0` и `or r7, r0`
blocks, cur, regs = [], None, {}
pc = 0
while True:
    op, a, b, c = data[CODE + pc:CODE + pc + 4]
    pc += 4
    if op == 0xff:
        break
    if op == 8:                      # read r0 — начало нового символа
        cur = []
        blocks.append(cur)
    elif op == 1:                    # mov r1, k — запоминаем константу
        regs[a] = b
    elif op == 6:                    # add r0, k
        cur.append(('add', b))
    elif op == 7:                    # xor r0, k
        cur.append(('xor', b))
    elif op == 4:                    # sub r0, r1
        cur.append(('sub', regs[b]))
    # op 10 (or r7, r0) просто закрывает блок

# 2. Идём от 0 назад через обратные операции
inverse = {
    'add': lambda x, k: (x - k) & 0xff,
    'sub': lambda x, k: (x + k) & 0xff,
    'xor': lambda x, k: x ^ k,
}
flag = ''
for ops in blocks:
    x = 0
    for name, k in reversed(ops):
        x = inverse[name](x, k)
    flag += chr(x)

print(len(blocks), flag)
```

```
$ python3 solve.py chall
55 flag{M4yb3_w3_c4n_74k3_0n_3v3n_70ugh3r_ch4113ng3$_n0w?}
```

Работает и тупой перебор: символы независимы, и на каждый хватает 256 прогонов блока в эмуляторе, то есть 55 × 256 = 14 080 вариантов. Именно так флаг был найден в первый раз, и для каждого символа подошло ровно одно значение. z3 или angr тоже справятся, но здесь они избыточны.

## Проверка

Бинарник принимает флаг. Если заменить хотя бы один символ, ответ меняется на `Wrong...`:

```
$ echo 'flag{M4yb3_w3_c4n_74k3_0n_3v3n_70ugh3r_ch4113ng3$_n0w?}' | ./chall
Input: Correct!

$ echo 'flag{M4yb3_w3_c4n_74k3_0n_3v3n_70ugh3r_ch4113ng3$_n0w!}' | ./chall
Input: Wrong...
```

Рецепт для похожих задач с VM: найти цикл диспетчера и таблицу переходов, выписать семантику опкодов и написать дизассемблер. После этого обычно видно, что символы проверяются независимо. Тогда хватает обратных операций или перебора по одному байту.
