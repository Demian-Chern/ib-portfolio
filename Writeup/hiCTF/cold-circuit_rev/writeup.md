# Cold Circuit — врайтап

Nov 1, 2026 · @Demian · Категория: Reverse

Флаг: `hiCTF{6e305f6a7461675f6e65656465642121}`. Проверка — самописный 20-раундовый шифр из обратимых шагов, поэтому флаг вычисляется обратным проходом от эталона, без перебора.

## Условие и разведка

Дан один файл `check` — 64-битный ELF (PIE, stripped). Флаг передаётся аргументом или через stdin, в ответ печатается `Access granted.` или `Incorrect.`.

```
$ file check
check: ELF 64-bit LSB pie executable, x86-64, dynamically linked, stripped

$ strings -n 4 check
...
hiCTF{
no input
Bad format.
unreachable
Access granted.
Incorrect.
```

Что видно сразу:

- Импорты `fgets`, `strlen`, `memcmp`, `puts` — проверка идёт локально, без сети и файлов.
- Импорт `ptrace` — почти наверняка антиотладка.
- Строка `hiCTF{` — префикс флага.
- Строка `unreachable` — подозрительная ветка, к ней вернёмся.

Флаг в открытом виде не хранится, значит, проверку надо разобрать. Код маленький (`.text` около 1,7 КБ), так что хватает `objdump -d -M intel check`. Адрес `main` берётся из вызова `__libc_start_main` в точке входа: `0x1431`.

## Формат флага

Флаг — это `hiCTF{` + 32 hex-символа + `}`, всего 39 символов. Это видно из функции разбора по адресу `0x12d6`. Ввод берётся из `argv[1]`, а если аргумента нет — из stdin через `fgets`.

Восстановленный код:

```c
int parse(char *s, uint8_t out[16]) {
    size_t n = strlen(s);
    while (n && (s[n-1] == '\n' || s[n-1] == '\r')) n--;
    if (n != 39)                    return -1;
    if (memcmp(s, "hiCTF{", 6))     return -1;   // строка по 0x2290
    if (s[n-1] != '}')              return -1;
    for (int i = 0; i < 16; i++) {
        int hi = hexval(s[6 + 2*i]);   // hexval — функция 0x1283
        int lo = hexval(s[7 + 2*i]);
        if (hi < 0 || lo < 0)       return -1;
        out[i] = (hi << 4) | lo;
    }
    return 0;
}
```

Итог: содержимое скобок — 16 байт в hex (регистр не важен). Эти 16 байт дальше и проверяются. При ошибке формата программа печатает `Bad format.` и выходит с кодом 2.

## Ловушки

В `main` две ловушки. Первая ломает проверку под отладчиком, вторая только отвлекает внимание.

### Антиотладка через ptrace

```c
int traced = 0;
errno = 0;
if (ptrace(PTRACE_TRACEME, 0, 1, 0) == -1 && errno == EPERM)
    traced = 1;
...
memcpy(rk, ROUND_KEYS, 320);    // 0x2140
if (traced) rk[0][0] ^= 1;
```

Процесс можно трассировать только одним отладчиком. Под gdb вызов `PTRACE_TRACEME` возвращает −1 с `EPERM`. Программа не падает и ничего не пишет, а молча меняет один бит первого раундового ключа. В итоге под отладчиком даже правильный флаг даёт `Incorrect.`, а ключи, снятые из памяти, оказываются неверными.

Как обойти, если нужна отладка:

- брать ключи не из памяти, а статически из `.rodata` (так сделано в этом решении);
- в gdb после вызова `ptrace` выполнить `set $rax = 0`;
- запатчить условный переход по адресу `0x154c` на безусловный `jmp`.

### Ложная ветка `unreachable`

```c
int x = argc + state[0];
if (((x*x + 1) & 3) == 0) { /* портит state */ puts("unreachable"); return 99; }
if ((x*x) % 4 == 2)        { return 98; }
```

Оба условия — непрозрачные предикаты (opaque predicates). Квадрат целого числа по модулю 4 равен только 0 или 1. Поэтому x² + 1 никогда не делится на 4, а x² mod 4 никогда не равен 2. Переполнение 32-битного умножения ничего не меняет: два младших бита произведения не зависят от старших. Обе ветки мёртвые, их можно пропустить.

## Алгоритм проверки

16 байт из флага проходят 20 раундов из трёх шагов (SPN-схема), результат сравнивается с эталоном. Все константы лежат в `.rodata`. В этом бинарнике виртуальный адрес `.rodata` совпадает со смещением в файле, так что таблицы читаются прямо из файла.

```c
uint8_t st[16];                 // 16 байт из флага
for (int r = 0; r < 20; r++) {
    for (int i = 0; i < 16; i++) st[i] += rk[r][i];      // 1. сложение с ключом mod 256
    for (int i = 0; i < 16; i++) st[i] = SBOX[st[i]];    // 2. замена через S-box
    uint8_t tmp[16];
    for (int i = 0; i < 16; i++) tmp[PERM[i]] = st[i];   // 3. перестановка байтов
    memcpy(st, tmp, 16);
}
uint8_t diff = 0;
for (int i = 0; i < 16; i++) diff |= st[i] ^ TARGET[i];
puts(diff == 0 ? "Access granted." : "Incorrect.");
```

| Адрес | Размер | Содержимое |
| --- | --- | --- |
| `0x2020` | 256 Б | `SBOX`, начинается с `85 dd 94 f6 …` |
| `0x2120` | 16 Б | `PERM` = 10, 8, 4, 14, 6, 7, 3, 0, 9, 5, 1, 13, 15, 11, 12, 2 |
| `0x2140` | 320 Б | `rk`: 20 раундовых ключей по 16 Б, первый — `8d c4 d8 29 …` |
| `0x2280` | 16 Б | `TARGET` = `97 67 14 88 0a 50 0d 16 0a 21 f6 95 0e ef 34 81` |
| `0x2290` | 6 Б | строка `hiCTF{` |

Сравнение через накопление `diff |= a ^ b` идёт за постоянное время. Побайтно подобрать флаг по времени ответа не выйдет, а полный перебор 2¹²⁸ вариантов нереален. Зато все три шага раунда обратимы — на этом строится решение.


Обратный проход начинается с `TARGET` и повторяет шаги раунда в обратном порядке, от последнего ключа к первому.

## Обращение и скрипт решения

Каждый шаг раунда имеет обратный, поэтому флаг получается проходом от `TARGET` с 20-го раунда по 1-й. Внутри раунда шаги тоже идут в обратном порядке.

| Прямой шаг | Обратный шаг | Почему обратим |
| --- | --- | --- |
| `tmp[PERM[i]] = st[i]` | `st[i] = tmp[PERM[i]]` | `PERM` — перестановка чисел 0–15, все значения разные |
| `st[i] = SBOX[st[i]]` | `st[i] = INV[st[i]]` | `SBOX` — биекция: все 256 значений разные |
| `st[i] += rk[r][i]` | `st[i] -= rk[r][i]` | сложение по модулю 256 |

Обратный S-box строится одной строкой: `INV[SBOX[i]] = i`. Ключи берём из файла без искажения `^ 1` — оно срабатывает только под отладчиком.

`solve.py`:

```python
import sys

data = open(sys.argv[1], 'rb').read()
ro = lambda addr, n: data[addr:addr + n]   # .rodata: адрес == смещение в файле

sbox   = ro(0x2020, 256)
perm   = ro(0x2120, 16)
rk     = ro(0x2140, 320)
target = ro(0x2280, 16)

assert len(set(sbox)) == 256, 'S-box не биекция'
assert sorted(perm) == list(range(16))

inv = [0] * 256
for i, v in enumerate(sbox):
    inv[v] = i

s = list(target)
for r in reversed(range(20)):
    s = [s[perm[i]] for i in range(16)]                    # отменить перестановку
    s = [inv[b] for b in s]                                 # обратный S-box
    s = [(s[i] - rk[r * 16 + i]) & 0xff for i in range(16)] # вычесть ключ

print('hiCTF{' + bytes(s).hex() + '}')
```

Запуск:

```
$ python3 solve.py check
hiCTF{6e305f6a7461675f6e65656465642121}
```

## Проверка и флаг

`check` принимает найденный флаг и в аргументе, и через stdin. Код возврата при этом 0.

```
$ ./check 'hiCTF{6e305f6a7461675f6e65656465642121}'
Access granted.

$ echo 'hiCTF{6e305f6a7461675f6e65656465642121}' | ./check
Access granted.

$ ./check 'hiCTF{00000000000000000000000000000000}'
Incorrect.
```

Флаг: `hiCTF{6e305f6a7461675f6e65656465642121}`

Hex-часть в ASCII читается как `n0_jtag_needed!!` — намёк на то, что аппаратная и программная отладка здесь не нужна, хватает статического анализа.

## Выводы

- Если каждый шаг проверки обратим, флаг не подбирают, а вычисляют от эталона в обратном порядке.
- Перед обращением стоит проверить, что S-box — биекция, а перестановка настоящая. Иначе у обратного шага будет несколько вариантов, и придётся перебирать их или подключать SMT-решатель (z3).
- `ptrace(PTRACE_TRACEME)` в импортах — сигнал не доверять тому, что видно в отладчике. Константы надёжнее брать из файла.
- Ветки с условиями вроде x² mod 4 лучше сначала проверить на выполнимость: часто это мёртвый код для отвлечения.
