# snaptool — reversing write-up

> **Категория:** Reverse Engineering
> **Флаг:** `hiCTF{r3c0nstruct3d_th3_sn4pf1l3_by73_by_by73}`

## Условие

Команда написала свой компактный бинарный контейнер для снапшотов — `.snap` — и
утилиту `snaptool` на Crystal, которая его валидирует и распаковывает. Наружу утёк
только сам инструмент: один **stripped**-релизный бинарник. Ни исходников, ни
спеки, ни примера `.snap`.

```
./snaptool somefile.snap
```

При успехе печатает распакованную метку (label) — это и есть флаг, при любой
ошибке — `invalid snapfile`. Других опций и диагностики нет.

Задача: собрать такой `.snap`, который утилита посчитает «настоящим».

---

## 1. Первичная разведка

```bash
file snaptool
# ELF 64-bit LSB executable, x86-64, dynamically linked, stripped

ldd snaptool
#   libcrypto.so.3 => ...        <-- OpenSSL
```

Строки подтверждают, что это Crystal-бинарник, и в нём есть искомое
`invalid snapfile`. Пробный запуск на мусоре ожидаемо даёт `invalid snapfile`.

Смотрим, какие функции импортируются из `libcrypto` — это сразу задаёт вектор:

```
EVP_get_digestbyname, EVP_DigestInit_ex, EVP_DigestUpdate,
EVP_DigestFinal_ex, EVP_MD_CTX_new, EVP_MD_get_size, ...
```

То есть вся «крипта» — это **только хеш** (message digest), без шифров. А строка
рядом с `EVP_get_digestbyname` — `"SHA256"`. Значит, формат держится на SHA-256.

---

## 2. Находим валидатор

`strace` показывает, что утилита читает весь файл в память одним `read(...32768)`
и дальше парсит в памяти — никаких `lseek`, структуру через I/O не вытащить.
Дизассемблируем и ищем, кто ссылается на строку `invalid snapfile`.

В Crystal строка — это объект с 12-байтовым заголовком (`type_id`, `bytesize`,
`length`), поэтому `lea` указывает на начало объекта, а не на символы:

```
file offset "invalid snapfile" = 0x61f7c
.rodata: foff 0x5d710 -> vaddr 0x45d710
=> строка-объект по адресу 0x461f70
```

Единственный xref — маленький стаб `0x436710`, который печатает строку и выходит.
Его вызывают из двух rescue-лендингов исключений. Сам же разбор формата лежит в
большой функции в районе `0x402xxx` (там, где три вызова SHA-256). Именно её и
читаем.

## 3. Разбор формата

### Общий размер

```asm
cmp ebp, 0x68      ; ebp = длина прочитанного файла
jne <error>
```

→ файл обязан быть **ровно 0x68 = 104 байта**.

### Заголовок `[0x00..0x0F]`

```asm
byte[0] == 'S'  byte[1] == 'N'  byte[2] == 'A'  byte[3] == 'P'   ; magic "SNAP"
word[4..5] (big-endian) == 0x0002                                ; версия = 2
byte[6] == 0x03
byte[7] == 0x00
```

Байты `[0x08..0x0F]` прогоняются через перестановку и сравниваются с константой
`0x534E41502D4C4E47`. Перестановка оказывается простым big-endian-переворотом:
восемь байт в обратном порядке дают эту константу. Эмуляция подтверждает, что
искомые 8 байт — это ASCII-строка:

```
file[8:16] = "SNAP-LNG"
```

### Таблица секций `[0x10..0x27]`

Отдельная функция читает 4-байтовые поля **big-endian u32** по фиксированным
смещениям и сверяет значения:

| Смещение | Значение | Смысл |
|---------:|---------:|-------|
| `0x10` | `0x28` (40) | off секции 1 |
| `0x14` | `0x10` (16) | len секции 1 |
| `0x18` | `0x38` (56) | off секции 2 |
| `0x1C` | `0x20` (32) | len секции 2 |
| `0x20` | `0x58` (88) | off секции 3 |
| `0x24` | `0x08` (8)  | len секции 3 |

Между полями есть явные связи, которые тоже проверяются:
`0x38 = 0x28 + 0x10`, `0x58 = 0x38 + 0x20`, `0x58 + 0x08 = 0x60`.

### Контрольная сумма `[0x60..0x67]`

```asm
h    = 0x1357BDF02468ACE1                 ; начальное состояние
prime= 0xD1B54A32D192ED03
for byte in file[8:96]:                   ; 88 байт
    h = ((byte + h) * prime)              ; mod 2^64
    h = (h >> 29) ^ h
; затем:
assemble_be64(file[96:104]) XOR h == 0x58
```

Это самодельный хеш (в духе wyhash/`xxh`). Так как последние 8 байт свободны,
их достаточно выставить в `h XOR 0x58`.

## 4. Где же флаг

Важный вывод: метка (флаг) **не хранится в файле**. Она вычисляется внутри тула
по бинарно-зашитым данным, а файл лишь «отпирает» её корректной шапкой:

```
seed  = SHA256(file[0x00:0x28])              ; первые 40 байт
mask  = MGF1-SHA256(seed, len)               ; SHA256(seed || counter), counter=0,1,2,...
label = CIPHERTEXT XOR mask                  ; CIPHERTEXT зашит в бинарнике
assert SHA256(label) == DIGEST               ; DIGEST тоже зашит
puts(label)
```

Ключевой момент: **первые 40 байт файла полностью зафиксированы** всеми проверками
выше (magic + версия + `"SNAP-LNG"` + таблица). Значит `seed`, а за ним `mask` и
сам `label` — детерминированы. Нам не нужно ломать SHA-256: достаточно воспроизвести
ровно те 40 байт, что были у «настоящего» файла, и тул сам распакует метку.

Байты `[0x28..0x5F]` (тело секций) ни на что из этого не влияют и на содержимое не
проверяются — ставим нули. Единственное, что нужно досчитать, — контрольная сумма
в хвосте.

## 5. Сборка файла

```python
import struct
M = (1<<64)-1
def u64(x): return x & M

def chash(buf):                      # кастомный хеш over file[8:96]
    h = 0x1357BDF02468ACE1
    p = 0xD1B54A32D192ED03
    for b in buf:
        r = u64((b + h) * p)
        h = u64((r >> 29) ^ r)
    return h

f = bytearray(104)
f[0:4]  = b'SNAP'
f[4:6]  = bytes([0x00, 0x02])        # версия 2 (BE u16)
f[6:8]  = bytes([0x03, 0x00])
f[8:16] = b'SNAP-LNG'
for off, val in [(16,0x28),(20,0x10),(24,0x38),(28,0x20),(32,0x58),(36,0x08)]:
    f[off:off+4] = struct.pack('>I', val)   # big-endian u32
# f[40:96] = нули (свободно)

target = u64(chash(f[8:96]) ^ 0x58)          # контрольная сумма = h ^ 0x58
f[96:104] = struct.pack('>Q', target)        # assemble = big-endian u64

open('genuine.snap', 'wb').write(f)
```

## 6. Результат

```console
$ ./snaptool genuine.snap
hiCTF{r3c0nstruct3d_th3_sn4pf1l3_by73_by_by73}
```

## Выводы

- Вся «защита» формата — набор константных проверок + самодельный 64-битный хеш для
  контрольной суммы.
- Крипто-«распаковка» метки детерминирована: она зависит только от первых 40 байт,
  которые однозначно задаются валидатором. Поэтому форсить SHA-256 не нужно —
  решение именно в **реконструкции файла байт за байтом**, что буквально зашито в флаг.
