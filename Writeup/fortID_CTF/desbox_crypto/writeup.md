## Recon

Сервис — эмулятор DOS-шелла (`DESBox.py`), работающий через TLS (`ncat --ssl`). Доступные команды: `DIR`, `TYPE`, `KEYB`, `DOOM`, `EXIT`.

Ключевая логика — в команде `KEYB` (`run_keyb()`):

```python
def xor(a, b):
    return bytes(x ^ y for x, y in zip(a, b))

def permute(a):
    p = list(range(len(a)))
    RNG.shuffle(p)
    return bytes(a[i] for i in p)

def load_key(user_key):
    key = xor(permute(user_key), MASK)
    return DES3.adjust_key_parity(key)
```

Пользователь вводит два 24-байтных (3DES, Option 1) ключа `KEY A` и `KEY B`. Каждый:

1. случайно переставляется побайтово (`permute`, своя случайная перестановка для A и для B);
2. XOR'ится с секретным `MASK` (неизвестная константа);
3. корректируется parity-бит (`DES3.adjust_key_parity`).

Дальше сервис:

- шифрует `FLAG` полученным `key_a` (ECB) и печатает шифртекст;
- принимает произвольный «debug ciphertext» и расшифровывает его `key_b`.

Перед принятием ключей `read_keys()` накладывает 4 проверки на **сырые** (введённые) ключи:

```python
if key_a == key_b: ...                                             # не равны
if effective_bytes(key_a) == effective_bytes(key_b): ...           # не равны по 7 старшим битам байта
if sorted(effective_bytes(key_a)) == sorted(effective_bytes(key_b)): ...  # не одно мультимножество байт
if is_effective_complement(key_a, key_b): ...                      # не побитовый комплемент друг друга
```

`effective_bytes` маскирует младший (parity) бит каждого байта — то есть проверки оперируют 56 значащими битами каждого подключа, как и сам DES.

## Анализ

### Свойство комплементарности DES

Классическое свойство DES: инверсия ключа **и** открытого текста даёт инверсию шифртекста:

```
E(~K, ~P) = ~E(K, P)
```

Свойство линейно переносится на 3DES (EDE), если инвертировать **весь** 24-байтный ключ целиком (все три подключа). Тогда из `C = E(key_a, FLAG)` следует:

```
D(key_b, ~C) = ~FLAG,  если key_b == ~key_a
```

То есть если добиться, чтобы производный `key_b` оказался побитовым дополнением производного `key_a`, достаточно подать на `Debug ciphertext` инверсию показанного шифртекста и инвертировать результат — получится `FLAG`.

### Проблема: permute() и проверка is_effective_complement

Напрямую ввести `key_b_raw = ~key_a_raw` нельзя — поймает `is_effective_complement`. А даже если бы прошло — `permute()` перемешивает байты ключа *после* проверки, случайной и неизвестной перестановкой, так что комплементарность сырых ключей не гарантирует комплементарность производных.

**Ключевое наблюдение:** если все байты ключа одинаковы, перестановка на него не влияет (перестановка одинаковых элементов — тождество). Значит, для константного ключа `x` производный ключ детерминирован и известен нам с точностью до `MASK`:

```
derived = x ⊕ MASK   (без какой-либо случайности!)
```

### Обход проверок: «почти константный» ключ

Строим пару:

```
key_a_raw = [p]*24, но key_a_raw[0]  = q     (p ≠ q)
key_b_raw = [~p]*24, но key_b_raw[1] = ~q    (другая позиция!)
```

Так как «особый» байт стоит на **разных** сырых позициях (0 и 1), `is_effective_complement` (сравнивает сырые байты попарно по индексу) не срабатывает. Остальные проверки тоже проходят тривиально (ключи не равны, не одно мультимножество и т.д.).

После перестановки на сервере особый байт `A` окажется на случайной позиции `i`, особый байт `B` — на случайной независимой позиции `j`. Во всех позициях, кроме `i` и `j`, оба ключа состоят из констант `p` и `~p`, так что комплементарность производных ключей там гарантирована автоматически. Единственная проблема — позиции `i` и `j`:

- если `i == j`, то на этой позиции встречаются особые байты `q` и `~q`, которые тоже комплементарны → **весь** производный ключ `key_b` оказывается точной побитовой инверсией `key_a`;
- если `i != j`, комплементарность ломается на этих двух позициях → расшифровка даёт мусор.

`i` и `j` — независимые равномерные случайные величины на `{0..23}`, так что `P(i == j) = 1/24 ≈ 4.2%`. Проверено локальной симуляцией серверной логики (с тестовыми `MASK`/`FLAG`): 90 успехов из 2000 попыток ≈ 4.5%, что соответствует теории.

При успешном совпадении:

1. читаем шифртекст `C = E(key_a, FLAG)`, который печатает сервер;
2. отправляем как «Debug ciphertext» значение `~C` (побайтовый XOR с `0xFF`);
3. сервер возвращает `D(key_b, ~C) = ~FLAG`;
4. инвертируем результат → `FLAG`.

Остаётся просто повторять команду `KEYB` с одной и той же парой ключей в рамках одной сессии (таймаут 120 сек), пока случайная перестановка не совпадёт по позициям.

## Эксплойт

```python
from pwn import *

HOST = "desbox-0defab48eba7.inst4.ctf.fortid.com"
PORT = 1337

p0, q0 = 0x00, 0x10
pp0, qq0 = p0 ^ 0xFF, q0 ^ 0xFF

key_a = bytearray([p0] * 24); key_a[0] = q0
key_b = bytearray([pp0] * 24); key_b[1] = qq0
key_a_hex, key_b_hex = bytes(key_a).hex(), bytes(key_b).hex()

io = remote(HOST, PORT, ssl=True)
io.recvuntil(b"C:\\>")

while True:
    io.sendline(b"KEYB")
    io.recvuntil(b"KEY A> "); io.sendline(key_a_hex.encode())
    io.recvuntil(b"KEY B> "); io.sendline(key_b_hex.encode())

    io.recvuntil(b"encrypted under Key A:\n")
    ct = bytes.fromhex(io.recvline().strip().decode())
    ct_comp = bytes(x ^ 0xFF for x in ct)

    io.recvuntil(b"Debug ciphertext> ")
    io.sendline(ct_comp.hex().encode())

    io.recvuntil(b"Debug output:\n")
    out = bytes.fromhex(io.recvline().strip().decode())
    candidate = bytes(x ^ 0xFF for x in out)

    if b"FortID{" in candidate:
        print("FLAG:", candidate)
        break

    io.recvuntil(b"C:\\>")

io.close()
```

## Выводы

- Случайная перестановка байт ключа (`permute`) не защищает от атак, если допустить **константные** пользовательские ключи — для них перестановка становится тождественной операцией, и итоговый ключ зависит только от известного пользователю значения и секретного `MASK`.
- Проверки на «симметричность» ключей (`is_effective_complement` и др.) оперировали только *сырыми, введёнными* значениями — что не помешало добиться нужного свойства на *производных* (post-permute) ключах через вероятностное совпадение позиций.
- Классическое свойство комплементарности DES/3DES (`E(~K,~P)=~E(K,P)`) остаётся рабочим инструментом даже в XOR/permutation-обёртках, если её можно свести к «инвертировать весь ключ».
