# gaslightCTF — ohfrick (rev)

## Категория
Reverse Engineering

## Дано
Один файл `code.py`:

```
Description: wtf happened to my source code!?
Author: sportshead
Attachments: code.py
```

Открыв файл, видим одну гигантскую строку — единственный `eval(...)` на
~47 тысяч символов, состоящий только из `[]`, `()`, `==`, `+`, `str`, `eval`.
Ни одной цифры, буквы или кавычки в явном виде.

## Что это за обфускация

Это автоматический обфускатор, который переписывает произвольный Python-код,
используя только шесть токенов:

- `True`/`False` собираются как `[]==[]` / `()==[]`;
- целые числа — суммой этих булевых значений (`([]==[])+([]==[])+...`);
- имена (`eval`, `str`, `input`, `int`, `ord`...) восстанавливаются
  посимвольно индексацией по строкам вида `str(eval)` (→ `"<built-in
  function eval>"`), `str(str)` (→ `"<class 'str'>"`) и т.п.;
- получившиеся строки склеиваются `+` и снова прогоняются через `eval`,
  чтобы получить реальные объекты/функции;
- весь процесс рекурсивно вложен друг в друга.

По сути — рабочая, не поломанная программа, просто отрендеренная в
максимально нечитаемый вид. Ничего вредоносного, задача чисто в том, чтобы
её распутать.

## Почему "в лоб" не работает

Первая идея — подменить `eval`/`exec`, чтобы залогировать, что именно
вычисляется на каждом шаге. Она проваливается: у `eval(source, globals,
locals)` и `exec()` неочевидная семантика значений по умолчанию (если
передан только `globals` — `locals` **не** берётся из фрейма вызывающего,
а становится равным этому же `globals`), и малейшая неточность в обёртке
меняет порядок вычислений/пространство имён и роняет скрипт с посторонними
`NameError`, которых в оригинале нет.

## Рабочий метод: `sys.settrace` + `dis`

Вместо того чтобы что-то подменять, скрипт запускается **полностью
нетронутым**, а `sys.settrace` используется только для *наблюдения*:
на каждом событии `call` проверяем, что новый фрейм — это динамически
скомпилированный код с `co_filename == '<string>'`, и сразу дизассемблируем
его через `dis.dis()`. Так поведение программы не меняется ни на йоту, но
видно точный байткод, который реально исполняется:

```python
import sys, dis, io

log = open('dis_log.txt', 'w')
seen = set()

def tracer(frame, event, arg):
    if event == 'call':
        code = frame.f_code
        if code.co_filename == '<string>' and id(code) not in seen:
            seen.add(id(code))
            buf = io.StringIO()
            old = sys.stdout
            sys.stdout = buf
            try:
                dis.dis(code)
            finally:
                sys.stdout = old
            log.write(buf.getvalue() + "\n")
    return tracer

sys.settrace(tracer)
sys.stdin = io.StringIO("test\n")   # чтобы input() не завис
exec(compile(open('code.py').read(), 'code.py', 'exec'), {'__name__': '__main__'})
```

Это сразу вскрывает финальный, настоящий байткод программы.

## Восстановленный исходник

Дизассемблировав финальный `<string>`-объект, получаем читаемый Python:

```python
f, i, o = input("f:"), int, ord
assert len(f) == 14

T = [
    f[8] == '_',
    i(f[1:3]) == 50,
    f[0] == str(True)[-1],
    f[5]+f[0]+f[9]+f[0]+f[3] == 'reset',
    f[12] + f[i(f[-1])**2] == str(credits).strip()[4:6],
]
F = [
    i(f[4]) + i(f[6]) != i(f[11]),
    o(f[7]) + 2 != o(f[0]),
    i(f[11]) % 2,
    str(None)[::-i(f[6])][:2] != f[0] + f[10],
    i(f[6]) ** i(f[i(f[6])]) > i(f[-1]),
]

assert all(T)
assert not any(F)
print('o' + f[-2])   # просто "ok" — сам флаг программа не печатает
```

Важный момент: `print` в конце выводит **не флаг**, а просто индикатор
успеха (`"ok"`). Сам флаг — это и есть строка `f`, которую ввёл игрок:
её нужно подобрать так, чтобы пройти все `assert`.

## Решение уравнений

Раскладывая условия по символам `f[0..13]` (индексация с нуля, длина 14):

- `f[0] == str(True)[-1]` → `str(True) = "True"` → **`f[0] = 'e'`**
- `f[5]+f[0]+f[9]+f[0]+f[3] == 'reset'` → сопоставляя буквы `"reset"`:
  **`f[5]='r'`, `f[9]='s'`, `f[3]='t'`**
- `int(f[1:3]) == 50` → **`f[1]='5'`, `f[2]='0'`**
- `f[8] == '_'` → **`f[8]='_'`**
- `ord(f[7])+2 == ord(f[0])` → `ord('e')=101` → `ord(f[7])=99` →
  **`f[7]='c'`**
- `str(credits).strip()[4:6]` — константа CPython (текст про "Thanks to
  CWI, CNRI, BeOpen.com..."), вычисляется напрямую: равна **`'ks'`**.
  Значит `f[12]+f[int(f[-1])**2] == 'ks'` → **`f[12]='k'`**, а поскольку
  `f[9]='s'`, нужно `int(f[-1])**2 == 9` → **`f[13]='3'`**
- Условие с `'None'[::-int(f[6])][:2] == f[0]+f[10]` ограничивает
  `f[6]` только значениями `'1'` или `'2'` (иначе срез даёт не 2 символа),
  и определяет `f[10]` через это.
- Оставшиеся `f[4]`, `f[6]`, `f[10]`, `f[11]` на самом деле однозначно
  довязываются через условие со срезом `str(None)[::-int(f6)][:2]`:
  `'None'` в обратную сторону с шагом `-1` даёт `'enoN'`, первые два символа
  — `'en'`. Значит при `f6='1'` требуется `f0+f10 == 'en'` → так как
  `f0='e'` (уже найдено выше), получаем **`f10='n'`**. Дальше из
  `int(f4)+int(f6) == int(f11)` при известном `f6='1'` и требовании, что
  `f11` — чётная цифра: `f4+1=f11` → минимальный/единственный рабочий
  вариант **`f4='3'`, `f11='4'`**. Система оказалась полностью
  определённой, без неоднозначности — более ранняя версия этого райтапа
  ошибочно посчитала её недоопределённой.

## Выводы / чеклист для похожих заданий

1. Если код состоит буквально только из `[] () == + str eval` — это
   известный класс "boolean-only" обфускаторов, а не что-то уникальное.
   Не пытаться распутывать вручную взглядом.
2. Не патчить `eval`/`exec` напрямую — их семантика умолчаний легко
   ломает порядок выполнения и даёт ложные ошибки.
3. Безопасный способ подсмотреть реальную логику — `sys.settrace` на
   событии `call`, фильтр по `frame.f_code.co_filename == '<string>'`,
   и `dis.dis()` каждого нового кодового объекта. Это не меняет поведение
   программы ни на бит.
4. Если получившийся чекер — система уравнений над символами строки,
   решать по частям (буквенные равенства → напрямую, числовые — через
   `int()`/`ord()` арифметику), и там, где система недоопределена —
   перебирать оставшиеся варианты и проверять их **реальным запуском**
   оригинального скрипта, а не только теоретически.
